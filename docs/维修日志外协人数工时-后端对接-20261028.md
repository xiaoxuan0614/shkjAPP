# 维修日志外协人数、工时

按用户确认，前端先复用项目实施日志的 `outsources` 结构。以下是新增对接约定，不代表后端现已支持。

## 保存接口

以下接口请求体新增 `outsources`：

- POST `/repair/work/saveDraft`
- POST `/repair/work/submit`
- POST `/repair/work/update`

```json
{
  "orderId": "维修单ID",
  "recordId": "本次签到维修记录ID",
  "persons": [{ "personType": "EXTERNAL", "sourcePersonId": "外协单位ID" }],
  "outsources": [
    {
      "outsourceMemberId": "本维修单外协成员记录ID",
      "headcount": 2,
      "workHours": 1.5,
      "remark": "本次实际参与说明（选填）"
    }
  ]
}
```

- `outsourceMemberId`：维修详情 `members[].id`，不能使用外协单位 sourcePersonId，也不是项目的外协记录ID。新增选择通过 personOptions 的 sourcePersonId 匹配 ACTIVE 外协成员记录。
- `headcount`：本次实际人数，正整数。
- `workHours`：本次实际工时，单位 h，正数；同项目字段原值传递，前端不乘人数、不把它直接算入维修人员签到总时长。单人工时/总人时的统计口径请后端与项目保持一致并明确。
- `remark`：选填，前端限制1000字符。
- 无外协参与传 `outsources: []`；update 按全量替换处理，空数组清除该次记录旧外协用人明细。persons 仍保留原有内外协标识，不用此字段代替外协统计，也不要重复统计。
- 草稿允许 headcount/workHours 为 null，正式提交/修改必填且大于0。后端需校验成员属于该维修单、权限及协助有效状态，防止跨单ID与重复成员。

## 详情回读

GET `/repair/work/detail?orderId=...&recordId=...` 返回上述 `outsources`，建议每条额外返回 `unitName` 快照；persons 继续返回原 personType/sourcePersonId/name，供稳定关联与历史回显。成员历史需保留，不因结束协助删除。

前端已完成实际人数、工时、备注输入；重选保留原输入；编辑按 outsources 回填；日志详情显示人数/工时/备注。缺少历史成员映射时不要改用单位ID冒充成员ID。

## 验证边界

页面排版同步项目实施日志：是/否分段选项、内协姓名多选标签、外协分条浅底区域；实际人数和工时并排，单位独立显示，备注在下方，末尾删除本条。保留维修已生效候选范围与原提交字段。布局检测、组件编译和用人/用料回归通过；本次布局未在真实签到日志中做浏览器验收。

定向测试通过：字段与项目一致、成员ID映射、数值校验、草稿空值、回填和重选保留；维修资源组件/接口回归及 diff 检查通过。尚未和后端实际保存回读联调，后端未接收这些字段时不能宣称数据已持久化。
