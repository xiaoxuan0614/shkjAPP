# 维修汇总与人员日志接口需求（前后端对齐稿）

前端已调整为：**维修详情展示整单维修汇总 → 查看详情进入人员维修记录 → 点击记录查看单条日志**。请补齐整单汇总和服务端分页，不再依赖维修详情内的 `workRecords` 数组计算整单统计。

以下“已有接口”沿用现有实现；新增接口路径、字段和统计规则为本次推荐契约，请后端确认并更新 Apifox 后通知前端对接，不代表已上线。

## 一、接口安排

| 接口 | 现状 / 本次需求 |
| --- | --- |
| `GET /repair/order/detail?id={orderId}` | 已有；建议返回 `workSummary`，同一次请求带回整单维修汇总 |
| `GET /repair/work/page` | **建议新增路径，待确认**；按维修单、人员查询维修日志，真正服务端分页 |
| `GET /repair/work/detail?orderId={orderId}&recordId={recordId}` | 已有；保留单条详情及操作权限，核对下文详情字段 |
| `GET /repair/order/logs` | 已有工单动态 / 处理时间轴，与人员维修日志不同，不用它代替人员日志列表 |

## 二、维修汇总

建议在维修详情 `result.workSummary` 返回：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `participantCount` | integer / null | 实际参与维修的内部人员去重人数 |
| `workRecordCount` | integer / null | 有效维修作业记录数，页面文案“维修次数” |
| `effectiveDurationSeconds` | integer / null | 整单累计有效人工工时，单位秒 |
| `latestWorkAt` | datetime / null | 最近一次有效作业开始时间 |
| `activeRecordCount` | integer / null | 尚未签退的有效作业数，供提示工时尚未计齐 |

维修状态和当前维修人继续用 `order.workStatus/responsibleUserId/responsibleUserName`，不要另造一套状态。

目前已有 `order.effectiveDurationSeconds`。请明确是否就是上述整单人工工时：如是，可保留旧字段并在 `workSummary` 返回相同值；如不是，必须说明旧字段口径，不能用同名字段返回另一种时长。两处同时存在时必须一致，最终以前后端确认的唯一字段为准。

**空值约定：**真实统计为零返回 0；未提供、无权查看或无法统计返回 null，并区分权限原因。没有任何有效记录时 `latestWorkAt=null`，前端显示“暂无维修”；不得用创建时间或当前时间填充。建议返回 `summaryAvailable` 或等价权限/可用性标识，让前端区分无数据与未提供。

## 三、推荐统计口径（请逐项确认）

1. **统计范围**：整张维修单，包括负责人变更前、已退出协助人员的历史有效记录。不能只算当前成员，也不能把当前账号可见的一页日志当作整单统计。
2. **参与人数**：建议按有效作业记录的 `operatorUserId` 去重；负责人、内协实际打卡后均计入。仅受邀、已审批但未作业的不计入。用人记录中的参与者不再次叠加，避免重复。若业务要求把未打卡用人也计入，请另明确去重规则。外协单位及填写的人数不能当成内部用户去重人数，可另返回外协人数统计。
3. **维修次数**：一条有效 `recordId` 算一次作业，包含进行中和已签退；同一记录保存草稿、提交、修改、补签退不增加次数。草稿属于已签到的同一次作业，不单独计数。取消/作废/被替代的记录不计入，后端需明确哪些实际状态排除。多人同时各有一条作业记录按多次作业计，不解释为“上门次数”。
4. **累计维修工时**：建议累计已签退记录的后端有效时长，进行中暂不计入结算工时，同时返回 `activeRecordCount`。补卡以审核生效后的有效时间为准，原始打卡和补卡不重复累加。多人并行各算各自人工工时，例如两人各 1h，合计 2h，不是自然历时 1h。相同人员的重叠作业应由后端校验/处理，前端不自行扣减。若现有后端有不同口径，请返回口径说明后再统一。
5. **最近维修时间**：取所有有效记录的 `effectiveStartedAt` 最大值；无修正时使用原始开始时间。不是最近修改日志时间、审批时间或最近签退时间。
6. **过滤影响**：人员筛选只影响人员日志列表及其 `total`，不改变详情中的整单汇总。
7. **权限**：只有允许查看整单汇总的账号才能获取整单数据；不能为了统计泄露无权查看的人员明细。如果只能返回权限内统计，必须显式标识统计范围，前端不能标成“整单”。关闭、完工单的合法历史查看权限要保留。

## 四、人员维修日志分页

### 请求参数（建议 `GET /repair/work/page`）

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `orderId` | 是 | 维修单 ID |
| `operatorUserId` | 否 | 记录操作人；不传表示全部可见人员，非当前维修负责人 |
| `pageNo` | 否 | 默认 1 |
| `pageSize` | 否 | 前端目前每页 5 条；建议默认 5、最大 100 |

人员筛选改变后从第一页开始；`total` 为筛选后的总条数，不是本页长度。空页返回 `records:[]`，不得报错。建议按有效开始时间倒序、`recordId` 倒序稳定排序；相同时间不能导致跨页重复或漏项。

### 返回字段

沿用现有 `{success, code, message, result}` 外层，`result` 建议为：

```json
{
  "records": [],
  "total": 0,
  "pageNo": 1,
  "pageSize": 5,
  "personOptions": []
}
```

`records` 每条至少提供：

| 字段 | 说明 |
| --- | --- |
| `recordId` | 作业唯一 ID；若沿用 `id` 请明确，前端需用于查详情 |
| `orderId` | 所属维修单，便于核对，防止串单 |
| `operatorUserId` | 操作人 ID，筛选用 |
| `operatorNameSnapshot` | 操作人历史姓名，沿用已有字段即可；不得用当前负责人名覆盖历史 |
| `workRole` | 本次作业身份，沿用现有枚举，负责人 / 内协等 |
| `repairMethod` | 线上、线下、检修，沿用现有枚举及字典文本 |
| `recordStatus`、`formStatus` | 作业与表单状态分开返回，不让前端根据描述猜状态 |
| `effectiveStartedAt`、`effectiveEndedAt` | 有效签到/签退时间；未签退结束时间为 null |
| `rawStartedAt`、`rawEndedAt` | 如需要保留原始打卡对照，可沿用已有字段 |
| `durationSeconds` | 本次后端计算的有效时长；未结算可为 null，不能伪造 0 |
| `repairDescription` | 维修内容；如返回截断摘要，请增加独立 summary 字段，详情返回全文 |

`personOptions` 每项 `{userId, userName}`，取本单全部**可见历史作业人员**，不只取当前页、当前成员或当前筛选结果。删除/停用/退出人员的可见历史仍应有姓名快照。同名不同 ID 分开，缺姓名不把 ID 当人名。

## 五、单条维修日志详情

沿用 `/repair/work/detail`，同时传 `orderId` 和 `recordId`。需要保证：

- 返回 `orderId/recordId`、操作人 ID/姓名、本次身份及维修方式、作业/表单状态。
- 打卡的原始时间、有效时间、`durationSeconds`；维修内容 `repairDescription`，负责人填写的故障描述 `faultDescription`。
- 照片/视频 `fileIds/files`，沿用现有可预览附件字段和权限。
- `persons`、`vehicleValue` 及可显示车牌信息；`materialItems` 回显 `pickLinkId/quantity/description`，并提供物料名称、规格、品牌、单位的可解析来源。已确认用料的不可修改规则及状态需可判断。
- `actions.canSaveDraft/canSubmit/canUpdate/canEnd` 继续由后端返回；查看历史记录不等于可以修改。单条详情再次验证维修单与记录归属及访问权限。
- 内协只展示允许的本人打卡和维修内容，不因共用详情接口泄露负责人专属内容。

## 六、时间、兼容与验收

- 时间字段统一格式和时区，建议 ISO 8601 携带 `+08:00`；若维持现有无时区格式，请明确按北京时间解析。时长统一秒，前端显示 h，不按一天 8h 折算实际打卡时长。
- 兼容旧客户端：新增汇总/分页时，原 `workRecords` 和已有日志详情暂保留，不悄然截断原数组。前端确认切换后再讨论废弃。
- 请用以下场景验证：无人作业、多人并行、同一人多次复修、草稿多次保存、未签退、补卡生效、负责人转单、协助退出、无权查看、同名人员、筛选后多页、零工时和无工时、关闭单历史、长文本、附件权限。
- 请回复：采用的接口路径及字段结构、上述统计口径确认结果、实际枚举、可用的测试环境版本，并提供最新 Apifox 与一组脱敏响应。前端再将“待接口提供”及本地分页切换为正式数据。
