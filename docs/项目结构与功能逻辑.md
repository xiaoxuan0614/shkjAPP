## 1. 技术结构

两端同步增量（2026-09-13）：到货确认范围包含 PENDING_APPROVAL，使用 payback_node 字典。`reworkMaterials.ts` 提供当前返工资格与额外额度查询，领料携带 reworkId；`projectAcceptance.ts` 与 `ProjectAcceptancePopup.vue` 提供分期当前轮内/客户验收、历史附件预览、统一结果提交及重新内验。无新页面路由，嵌入 projectDetail。验收结果必传当前 acceptanceId，报告通过统一上传后随 complete 保存，不提前 edit。后端审批链和 APP 登录权限迁移仍有缺口，见 [两端规则同步与后端待办](项目两端规则同步与后端待办.md)。

还料申请（2026-09-13）：`src/pages/ops/materialReturn.vue` 无状态限制调用 `/project/member/participatedProjects`，本地模糊搜索主项目/分期名；按 `periodId` 分页读取 `/project/materialAccount/page`，用 `remainingReturnQty` 和 `baseUnitName` 展示可还物料。本次数量 0 跳过，部分还料填写差异原因。确认后 `/stock/apply/add` 提交 `applyType=IN/bizType=RETURN/usageType=PROJECT/periodId`、可选备注和明细 `materialId/unitName/unitQty/remark?`；不调用旧 `/ops/materialReturn/*`，不直接入库或审批。

本项目是 Vue 3 + TypeScript + Vite 的 uni-app 多端工程，使用 Pinia 保存登录用户，Wot Design Uni 提供业务组件。主要目录如下：

| ------------------- | -------------------------------------------------------------- |

### 1.1 登录链路

- 账号登录暂时移除图形验证码加载、输入和校验，按 SHKJ-OA 相同方式将密码做 AES-CBC/PKCS7 加密，仅提交 `username/password` 到 `POST /sys/login`。
- 短信登录通过 PC 端当前使用的 `POST /sys/sms` 发送登录验证码，再提交 `mobile/captcha` 到 `POST /sys/phoneLogin`。
- 登录成功必须同时取得 `result.token` 和 `result.userInfo.id`；移动端保存完整 `userInfo`，并从响应的 `departs` 解析当前部门名称，不再请求未收录于当前 Apifox 的 `/sys/user/appQueryUser`。
- 登录请求统一定义在 `src/service/auth.ts`，密码加密实现位于 `src/utils/cipher.ts`。认证成功后依次调用 `/sys/permission/getUserPermissionByToken` 和 `/sys/permission/getPermCode` 初始化菜单与按钮权限；认证、权限初始化需分别验证。
- PC 登录页还会调用 `/sys/loginGetUserDeparts` 做登录前多部门选择，但该接口未收录在当前 Apifox；移动端没有把它作为正式接口接入。若后端要求多部门用户登录前必选 `loginOrgCode`，需先在 Apifox 发布该契约后再增加选择 UI。

## 2. 标识与数据边界

- 2026-09-15 项目详情“项目实施”入口与实施选择页统一：当前分期必须在 `participatedProjects?onlyUnfinishedProcess=true` 结果中，并拥有 `/pages/ops/implementLog` 页面访问权限。入口不再复用 `project:implement` 操作权限或旧状态白名单；“实施完成”的权限检查保持不变。

- 2026-09-13 项目实施候选规则：`/project/member/participatedProjects` 传 `onlyUnfinishedProcess=true`，不再传 `periodStatus` 或按前端状态白名单筛选；选中分期后 `/project/process/detail` 传 `periodId + onlyUnfinishedProcess=true`。此规则覆盖下文旧实施候选状态描述，不影响领料等其他页面；签到前仍实时校验工序状态。

- 主项目使用 `projectId`，项目分期和移动端实施流程以 `periodId` 为主标识。
- 项目列表接口返回的 `periodId` 在移动端适配为页面通用 `id`，路由参数仍代表分期 ID。
- 项目列表展示的主项目编号优先读取 `projectNo`；领料申请契约中的 `projectNo` 提交所选分期的 `periodNo`，`projectName` 提交所选分期名称 `periodName`。这是当前 Apifox 的字段定义。
- 物料申请头与明细分开读取：申请头 `/stock/apply/queryById`，明细 `/stock/apply/items`。不得继续依赖已废弃的 `queryById.itemList`。
- 出入库执行统一提交 `{ applyId, itemIds?, items? }` 到 `/stock/apply/execute`，方向由申请头的 `applyType` 决定；部分执行通过 `items[{ itemId, executeQty }]` 指定本次数量。

- 还料、巡检、邀约和车辆新增记录：PC 端没有找到完整且一致的写入契约，暂保留 Mock/待接状态。

### 3.3 库管端 `src/pages/stock/`

- 首页出库执行待办按 `actionKey/todoType=STOCK_OUT_EXECUTE` 分流，使用 `actionParams.applyId` 跳转 `/pages/stock/materialDetail?id=...&from=stockOutTodo`，不使用 `bizId/bizSubId` 兜底。保留页面权限；详情按 `mtl:goods:io`、审批状态 `1` 和执行状态 `PENDING/PARTIAL_EXECUTED` 控制出库，提交前重查申请头。返回首页自动刷新待办列表及数量，页面仍由后端控制数据和操作权限。

- 列表按 `applyType=OUT/IN` 调用 `GET /stock/apply/list`。
- 详情并行调用 `GET /stock/apply/queryById` 和 `GET /stock/apply/items`。
- 待出库记录必须进入详情办理，不在列表直接执行整单。出库物料显示审批数量、实时库存、已出库数量、待出库数量；审批数量优先使用 `approvedQty`，历史空值回退申请数量，待出库数量为审批数量减 `executedQty`。

## 5. 接口依据与验证规则

接口事实源为 Apifox 项目 `8679942`。2026-08-25 已通过其当前公开接口文档逐项复核，并与 SHKJ-OA 当前开发环境和 API 封装交叉检查；PC 代码只作为调用方式参考，路径或字段冲突时以当前 Apifox 为准。每次联调至少验证：请求 URL、query/body 位置、字段名、业务 code、分页结构、空数据、无权限和页面回显。

普通业务页使用 uni-app 原生导航并传 `PageLayout :navbarShow="false"`；`PageLayout` 内置的自定义 `wd-navbar` 仅供弹层和明确需要自定义返回/右侧操作的页面使用，不删除组件结构。
