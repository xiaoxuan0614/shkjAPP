# 维修待办办理入口同步 PC

- 首页及全部待办的 `title / summary` 显示保持不变。
- `REPAIR_COLLABORATION_ASSIGN` 按 `applicationId + departmentId` 直接打开指定人员弹窗，不要求 `orderId`，不预先加载整张维修单。复用现有本部门候选及指定接口、最多 20 人、失败保留与请求重试逻辑；成功刷新待办。
- `WORKFLOW_APPROVAL` 的维修审批改为首页/全部待办直接打开 `RepairApprovalPopup`，不跳转维修详情。核对实例 ID、维修业务类型及维修单/申请 ID；非维修实例保留原有分流。旧待办无业务类型时先读实例识别，结果复用给弹窗，不重复读取。
- 弹窗和 PC 一致读取 `/workflow/instance/detail`、`/workflow/instance/actions`、`/workflow/instance/form`，校验表单版本，按字段权限展示内容，按后端 `canHandle / actions / disabledActions` 显示办理按钮。附件未能预览时阻止审批并提示到 PC 核对。
- 关闭、外协审批使用 `/workflow/instance/handle`；内协及转单使用 `/repair/application/review`。内协保留 `WITH_APPROVAL` 候选选人和审批后独立指定两种模式；转单按 PC `/repair/options?type=internal` 读取接收人，改选提交 `transferTargetUserId`。
- 同意/驳回先进入确认表单，驳回原因必填；提交前重新读取允许动作，保留请求 ID 与结果不确定时的同请求重试。成功提醒并刷新待办。标题摘要不变，已打开/加载中防重复进入，关闭加载中的弹窗不会锁死下一次打开。
- 未提供必需定位参数、实例不匹配或任务失效时明确报错，不根据标题猜测业务 ID，不放宽权限。

验证：首页、协助、审批弹窗脚本回归通过，H5 构建通过。浏览器当前账号实际点击维修关闭审批、外协邀请审批，均在首页直接打开，申请内容、当前节点及同意/驳回正常；外协已进入审批意见及“确认同意”表单，但未确认提交。指定内协人员弹窗也正常回显本部门候选及确认按钮，未选择或提交。
