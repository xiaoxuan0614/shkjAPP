# 出入库审批后取消对接

## 用户确认

全部审批通过、待执行的出入库单均应支持取消，包括维修领料、维修还料、项目及其他出入库；后端同步扩展。仅提交取消，不引入新的审批流。

## 当前 Apifox 与新增范围

已现场读取 `POST /stock/apply/cancel`：查询参数 `id`。现有文档明确支持 OUT+PROJECT、status=1 的未执行/部分执行剩余量终止，由申请人、库管或管理员办理；关闭执行状态、保留原申请/批准/已执行量及库存台账、不回退库存，已关闭幂等，待办及业务动态同事务。原待审批撤回保留；文档对 IN 仍写规则不变。

此次新增全部 IN/OUT 的 `status=1 && executeStatus=PENDING` 前端入口，按用户确认扩展，并非当前文档已承诺后端全部支持。其他业务部分执行取消未擅自放开，仍仅允许文档明确的 PROJECT OUT。

## 前端完成

- `materialDetail.vue` 的申请信息标题右侧显示撤回/取消/终止剩余领料，避免与底部执行按钮互斥导致库管看不到。
- 待审批保留本人撤回；已审批待执行允许本人或具有移动端出入库操作权限 `mtl:goods:io` 的账号办理。后端最终鉴权。
- 操作前确认说明，不要求新增原因字段；POST 查询参数 id 沿用既有封装。
- 确认后刷新权限并重查申请，资格或操作类型变化即停止；取消与出入库执行互斥。成功刷新详情，失败展示服务端原因，不在前端伪造取消状态。
- 已结束/关闭/全部执行及未知执行状态不开放取消。

## 后端配合

1. 将审批后待执行取消扩展至全部 IN/OUT 业务类型，维修单仍执行完工、关闭、转单冻结等约束。
2. 在事务中核对申请人/库管/管理员权限及状态；与并发出入库执行互斥校验，防止读取PENDING后实际已有执行仍按整单取消。
3. 成功后不能继续执行/编辑旧单，按业务释放待执行占用、关闭待办、写处理动态；保留审批与申请记录，不回滚实际库存。
4. 重复取消幂等，并更新 Apifox 的适用范围、成功后状态与错误说明。

## 验证

`node scripts/test-stock-cancellation.cjs` 通过：IN/OUT及各业务类型、本人/库管/无权限、待审批/待执行/已关闭/执行完成/未知状态、项目部分执行和状态二次核对，Vue模板/脚本编译通过。`git diff --check` 通过。未对真实申请提交取消，新增范围仍需后端联调。

## 最新用户规则（覆盖前文扩展权限范围）

仅申请人本人可取消；审批通过后的取消入口仅面向所有业务类型领料 OUT，status=1、executeStatus=PENDING。库管/管理员身份不作为代取消资格，不开放部分执行终止或已审批入库取消。待审批本人撤回保留。按申请人ID与当前用户ID严格匹配，缺少ID不回退同名判断。最新状态二次核对沿用同一规则。已删除多余的终止分支文案和库管权限参数。

专项及Vue编译检查通过，覆盖本人、他人、管理员/库管不越权、同名不同ID/缺ID、部分执行/已关闭与待审批。未真实取消业务单据。
