## 2026-10-16 最新调整：值班表自动分配

本节覆盖下方手工派单流程：报修提交后由值班表自动确定运维人员，首页不再提供维修派单入口，表单不再选择维修或勘查人员，删除待派单/已派单状态及转单入口。受理、勘查和报价由该运维人员跟进（管理员/负责人可在演示中办理）；内部报价确认仍由负责人办理。无需报价或内部确认通过后自动生成维修单，状态为待维修，沿用报修单值班人员。非故障关闭；报价未确认不生成维修单；已生成的不重复生成。

当前没有正式值班表接口。`assignDemoDuty` 仅按报修日期匹配三个示例人员，日期、人员与自动分配事件在详情中标为示例，不能作为正式排班算法。正式接入应由后端返回实际值班人员及分配结果，不使用本地示例规则。示例数据同步采用新状态；自动生成、报价前置条件和防重复检查通过，相关 SFC/SCSS 编译通过。

## 2026-10-16：报修受理、报价与派单调整（覆盖下方旧说明）

- `feat/op` 分支首页「日常办公」直接展示填写报修、报修列表、维修报价、维修派单、维修工单、巡检管理六个入口，不再限定开发环境或 admin 登录名。
- 所有登录账号可填写报修并查看本账号提交的记录。`operations_manager`、`admin` 可在演示中受理、填写勘查、创建报价、内部确认及派单。内部确认的正式审批人配置仍待接口契约，不代表已配置审批流。
- 受理分流：非故障填写说明后关闭；故障无需报价则待派单；需要报价则现场勘查 → 创建报价单 → 内部确认 → 待派单。报价退回需原因，修改后重新提交；确认之前不能派单。
- 指定示例运维成员和维修方式后，生成关联报修及报价的维修单，继续复用预约、维修日志、领还料等演示页面。维修表单不再自行修改报价状态，展示上游「无需报价 / 内部已确认」。普通报修用户不能执行其他人的维修工单。
- 报修、报价、派单页面共用内存数据，支持搜索、状态筛选、每页 5 条。返回首页保留本次数据；刷新、退出登录、切换账号或租户会清空。没有跨账号传递、服务端保存、真实派单通知或正式业务接口调用。成员仍为示例成员，不能通过切换真实账号验证派单接收。
- 新组件 `OpsIntake.vue` 与状态转换 `intakeFlow.ts`；原 `OpsPreview.vue` 保留维修和巡检，删除旧的直接接单生成维修单入口。沿用现有蓝白色、卡片、三列入口及移动表单样式。
- 本轮流程分支模拟、SFC/SCSS 编译检查通过；H5 构建使用 `CHOKIDAR_USEPOLLING=true` 通过。浏览器只有未登录会话，未完成真实账号及手机视觉验收。

## 入口与边界

用户确认当前没有对接文档，先完成页面。仅开发环境中登录名严格为 `admin` 的已登录账号，在首页显示「运维页面预览 → 查看墨刀运维页面」；其他账号（即使有管理员角色）不显示。入口及预览组件使用同一条件，退出或切换为其他账号时关闭预览。仍由 `import.meta.env.DEV` 限制开发环境，不发布为正式业务菜单，不新增或放宽角色权限。

源码位于 `src/pages/ops/components/preview/`，由首页内嵌全屏预览组件承载，没有变更原维修页面路由。设计依据为项目墨刀原型「小程序 → 运维人员」中的接单、预约、线上/线下维修、工单详情及巡检画布。沿用现有蓝白色、系统字体、分组表单和底部操作区，不另建视觉体系。

所有单号以 `DEMO-` 开头，客户、人员均明确标记示例。交互数据仅存组件内存，退出整个预览即清空；未完成表单在离开该表单时清空，页面已提示。没有恢复 Mock 服务、没有新增正式接口或伪造业务成功响应。
