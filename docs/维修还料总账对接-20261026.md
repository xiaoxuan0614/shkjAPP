# 维修还料总账对接

## 查询与展示

- 维修详情新增“用料统计”：复用 `/repair/materialAccount/page`，传 `orderId/pageNo/pageSize=5`，不传 handlerUserId，按整单读取。展开后查询，显示物料（品牌/型号/基准单位）、出库 outboundQty、已还 actualReturnQty、使用 consumedQty、可还 availableReturnQty。使用是用料占用合计，非仅已确认；无计划量列，不伪造维修计划数量。零值保留，缺失显示“—”，查询失败可重试，切单清空旧结果。还料入口仍按本人查询，两者不混用。

- 2026-10-27 修复维修还料入口：进入维修单还料表单即自动分页加载全部本人可还物料，不再等待点击“添加物料”。每次请求 10 条，完整加载后统一回填，数量默认 availableReturnQty；失败显示重试并禁止提交，切换维修单/人员及卸载使旧请求失效。保留手动调整物料与数量的入口。

- 还料物料候选使用 `GET /repair/materialAccount/page`，传 `orderId`、当前登录人 `handlerUserId`、`pageNo`、`pageSize=10`，搜索传 `keyword`。
- 2026-10-27 更新：只展示有效且 `availableReturnQty > 0` 的项，字段缺失不回退 `remainingReturnQty`。名称、编码、品牌、型号、单位读取 `materialName/materialCode/brand/model/baseUnitName`。
- 选择键使用 `materialId + baseUnitId`，避免不同历史基本单位覆盖；提交仍使用真实 `materialId`，不把选择键当物料 ID。
- 可还量、默认数量及前端上限均取 `availableReturnQty`。部分归还（包括填 0）需填写差异原因；至少一项大于 0。
- 当前提交协议仅按物料 ID 传数量，未确认历史单位区分协议，因此同一物料不同历史单位需分别申请，不合并提交。
- 领料继续使用原通用物料目录，维修还料提交仍走 `/stock/apply/add`，保留原还料单价及提交字段。

## 字段口径确认

2026-10-26 已阅读 Apifox 原生应用中的最新“维修：维修单物料总账（整单汇总/领料人筛选）”文档。文档说明 `remainingReturnQty` 为未扣待办占用的剩余待处置量，`availableReturnQty` 才是扣除占用后的当前可还量。

2026-10-27 用户明确改为 `availableReturnQty`，替代此前“跟项目一样”使用 `remainingReturnQty` 的口径。本次仅修改维修还料，项目还料保持原规则。最终权限、个人来源及实时余额仍由后端校验。

## 验证边界

自动测试覆盖接口参数、分页搜索、不同单位分行、零余额排除、可还量默认值、超量/差异原因校验、查询失败及原领料路径；新增 availableReturnQty 与 remainingReturnQty 不同及 availableReturnQty 缺失的用例。未提交真实还料申请，未发布部署。
