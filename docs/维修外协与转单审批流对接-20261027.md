# 移动端维修外协与转单审批流对接

依据：2026-10-27 Apifox 原生应用中的 `/repair/collaboration/submit`、`/repair/transfer/submit` 和 `/workflow/model/businessTypes` 文档。

## 外协协助

- 仍从维修详情“更多 → 邀请协助 → 外部协助”填写，每次一家单位。
- `POST /repair/collaboration/submit`：`orderId`、`personType=EXTERNAL`、`sourcePersonId`、`personCount`、`estimatedTotalHours`、`reason`。
- 人数为 1–10000 的整数；预计总工时大于 0、不超过 999999.99，最多两位小数。3 人总计 24 小时传 24，不乘人数。
- 不发送 `departments/userIds/roleId`，不发送旧 `headcount/hoursPerPerson`。
- 后端启动 `repair_ops_external`（场景 `REPAIR_EXTERNAL_COLLABORATION`），申请人所属部门主管一级审批，多主管 ANY，无主管 FAIL。前端不直接启动第二条审批实例。
- 只有审批通过后才生效；单位名以返回的 `unitName` 为准。申请详情/审批摘要显示人数和预计总工时。撤回或驳回后按新申请重提，不修改原审批历史。
- 旧历史人数/人均工时只读兼容，不自动换算旧申请后重提。

## 转单

- 接单人改为组织架构唯一有效“运维部”下的人员：`/sys/sysDepart/queryTreeList` 解析部门 ID，再分页请求 `/sys/user/list?departId=部门ID&pageNo=1&pageSize=100`（复用 PC 值班表协议）。排除当前维修人及已停用/删除人员；部门歧义、无权限或查询失败不回退全公司人员。提交仍由后端校验有效运维成员资格。

- 原提交地址已是 `POST /repair/transfer/submit`，本次保留：`orderId/targetUserId/reason`。
- 后端启动 `repair_ops_transfer`（场景 `REPAIR_TRANSFER`，业务类型 `REPAIR_OPS_APPLICATION`），运维主管审批通过后才更新负责人及待办。
- 增加提交前当前负责人、工单状态、操作权限与有效接单候选检查，排除当前维修人。重新打开转单时清空上次候选，防止加载失败沿用旧列表。
- 未签退、未完报价/协助等业务限制由后端最终校验；不绕过或前端假更新负责人。
- 补充转单专项回归：待办按申请/实例/任务 ID 进入审批；驳回必须填写原因、负责人保持不变；通过后采用服务端返回的新负责人，已完成任务不再可办理。上述为内存接口桩测试，不代表真实服务审批已联调通过。

## 审批与部署边界

### 关闭申请（2026-10-27 核对）

Apifox `/repair/close/submit` 已声明独立场景 `REPAIR_CLOSE`，固定流程 `repair_ops_close`。移动端保留当前负责人的关闭申请入口，必填关闭原因类别（客户弃修/不是问题/其他）与说明，提交 `orderId/closeType/reason`；增加原因枚举合法性校验。提交不在客户端修改工单状态。

审批继续走 `/repair/application/review`，按可办理任务定位，拒绝必填 comment；主管最终通过后只采用后端返回的 CLOSED 状态。未结束作业、未结清物料由后端在提交和审批时检查。关闭申请、审批待办定位、空原因拒绝、驳回保持原状态及通过后关闭已做接口桩回归；未真实发起关闭或发布审批模型。

两类申请继续复用维修详情中的 `applications/workflows/tasks.canHandle` 以及维修待办解析，审批走 `/repair/application/review`，携申请、实例、任务 ID。不额外调用通用工作流 start，不提交客户端 version/requestId。

协助表单、外协字段边界、审批摘要、重提、转单参数/负责人不提前变化、既有内协及待办路由回归通过。未用真实账号提交审批，也未发布/修改 PC 审批模型；正式环境须由后端部署并启用对应模型。模型是否已启用不能仅凭前端代码确认。
