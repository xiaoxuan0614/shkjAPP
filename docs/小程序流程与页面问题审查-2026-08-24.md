# 首汇科技小程序流程与页面问题审查

> 审查日期：2026-08-24  
> 审查对象：用户提供的 `实施日志.zip` 页面总图（5448×861）、墨刀只读原型、`JeecgUniapp` 当时页面与 Mock 接口。
>
> 状态说明：这是 2026-08-24 的方案审查记录，其中 `/project/implementationSession/*` 是当时建议的新后端契约，并非当前 Apifox 已存在接口。2026-08-25 实际实现以本地唯一会话保证页面续办，签退时调用 `/project/implementLog/add` 落库；当前事实请看 `项目结构与功能逻辑.md`。
> 核心结论：项目实施必须以一次“实施会话”为主线，形成 **签到 → 填写并提交实施日志 → 签退** 的强制闭环。当前工程把“实施日志”和“内协打卡”做成了两个独立功能，项目详情也没有承接进行中的实施会话，因此流程实际上没有闭合。
> 已确认产品决策：**删除独立“内协打卡”模块**；项目签到/签退并入项目实施闭环，线下维修自身的到岗签到不受影响。

## 0. `实施日志.zip` 原型核对结果

压缩包内的页面总图包含 12 个连续画面，原设计本身已经表达了完整闭环。当前工程的问题不是“原型缺少打卡”，而是实现时没有按这条连续路径落地。

| 顺序 | 原型画面 | 关键内容 | 审查结论 |
| --- | --- | --- | --- |
| 1 | 单号选择 | 单号、客户名称筛选；列表同时出现 XM、GZ 单号 | 项目实施应优先限制为可实施的 XM/项目周期，不应让用户自由混选维修故障单 |
| 2 | 到岗签到（未签到） | 人员、日期、地图、关联单号、重新定位、签到按钮 | 作为闭环起点正确；项目/工序应从入口自动带出 |
| 3 | 到岗签到（已签到） | 已签到状态、打卡时间/地点、下一步 | 正确表达“签到成功后才能进入日志” |
| 4 | 实施日志 1/3 | 项目名称、客户、联系人、当前工序、计划周期、剩余工期 | 项目上下文自动带出是正确方向，不应在日志页再次任意选项目 |
| 5 | 实施日志 2/3 | 实施位置、实施内容、现场照片、内协/外协人员与工时 | 现场证据较完整；需补必填、数值范围、草稿与失败恢复规则 |
| 6 | 实施日志 3/3 | 使用车辆、行驶公里、用料记录、完成 | “完成”应表示提交本次日志并进入待签退，不能直接结束整次实施 |
| 7 | 物料清单 | 申请数量、已用数量、选择/取消选择 | 需校验可用量、使用量上限、重复选择和并发库存变化 |
| 8 | 结束打卡（正常） | 当前时间、位置、重新定位 | 正确表达签退动作；只有日志提交成功后才允许进入 |
| 9 | 本次实施完成 | SG 实施单号、到场/结束时间、实施时长、查看日志 | 闭环结果页结构合理，建议再展示签到/签退定位状态 |
| 10 | 结束打卡（位置异常） | 红色异常状态、异常位置、重新定位 | 颜色和文案能提示风险，但不能只靠颜色区分 |
| 11 | 异常结束确认 | 位置异常原因输入、确认/取消 | 原因应必填，并保存定位精度、经纬度和异常类型 |
| 12 | 异常完成结果 | 完成摘要、异常原因、查看日志 | 原型误写为 `WX...`，项目实施单号必须为 `SG...` |

### 0.1 原型已经确认的正确业务规则

- 签到成功后才显示“下一步”；
- 日志是 3 步连续填写，而不是与打卡平级的孤立入口；
- 日志完成后进入结束打卡；
- 正常和位置异常两种签退均有结果页；
- 完成页汇总实施单号、到场时间、结束时间、实施时长，并提供“查看日志”；
- 项目、客户、当前工序、计划周期等上下文由系统自动带出。

### 0.2 原型自身需要修正的问题

1. **异常完成页单号前缀错误**：显示 `WX20250914092201`，应为 `SG...`；
2. **同组时间数据前后不一致**：签到按钮、签到记录、结束按钮与完成弹窗出现不同时间，交互稿应统一一套示例数据；
3. **单号选择混入 GZ**：如果此页专用于项目实施，应仅显示当前用户可实施的 XM/项目周期；维修签到由线下维修流程承载；
4. **术语需统一**：页面使用“到岗签到 / 结束打卡”，业务文档应统一为“签到 / 签退”，按钮可写“签到并开始实施 / 签退并完成本次实施”；
5. **缺少中断恢复说明**：未画出日志草稿、退出重进、跨天未签退、弱网提交失败等状态；
6. **缺少进行中总览**：建议在日志页顶部固定展示签到时间、已实施时长和当前工序；
7. **完成按钮语义模糊**：日志第 3 步按钮“完成”应改为“提交实施日志”，提交成功后明确提示“下一步：签退”；
8. **物料数量约束未体现**：需标明可使用上限、单位、零值处理及超量提示。

## 1. 结论先行

### 1.1 当前最关键的问题

当前实现存在三条互相平行、但没有建立约束关系的路径：

1. 工作台 → 实施日志 → 选择项目 → 直接提交日志；
2. 工作台 → 内协打卡 → 输入关联单号 → 签到或签退；
3. 项目列表 → 项目详情 → 开始实施 / 提交验收。

这会产生以下业务漏洞：

- 未签到也能写并提交实施日志；
- 已签到后没有明确的“继续写日志”入口；
- 日志提交后不会自动进入“待签退”；
- 未提交日志也能在打卡页签退；
- 日志和签到记录没有统一的实施会话标识，无法证明属于同一次现场实施；
- 项目详情只展示日志，没有展示签到、签退、定位、实施时长等闭环证据；
- “开始实施”和“提交验收”目前只是前端提示，没有真实状态流转。

### 1.2 正确的项目实施主流程

```text
进入项目详情 / 今日实施任务
  ↓
确认项目、当前工序和实施人员
  ↓
签到（时间 + 经纬度 + 地址 + 定位状态 + 现场照片可选）
  ↓
生成本次 implementationSessionId，状态 = 已签到/待填日志
  ↓
填写实施日志
  ├─ 项目与工序：系统带出，不允许重新选择其他项目
  ├─ 实施内容、位置、现场照片
  ├─ 内协/外协人员与工时
  ├─ 行车记录
  └─ 用料记录
  ↓
保存草稿 / 提交日志
  ↓
状态 = 日志已提交/待签退
  ↓
签退（时间 + 经纬度 + 地址 + 异常原因）
  ↓
状态 = 本次实施已完成
  ↓
形成完整记录：签到、日志、签退、时长、轨迹证据、实施单号 SG
```

### 1.3 不能绕过的规则

- 没有有效签到记录，不允许提交实施日志；
- 一个用户同一时间原则上只能有一个进行中的现场实施会话；
- 日志必须绑定签到生成的 `implementationSessionId`，不能只绑定项目 ID；
- 日志未提交时，签退按钮不可直接完成闭环；如确需提前离场，必须走“异常签退/取消本次实施”，填写原因；
- 签退成功后，本次日志默认不可随意修改；更正应保留修改记录；
- 再次进入页面时，应恢复进行中的会话，而不是重新让用户选择项目；
- 项目处于未开始、待验收、质保中、已完成或已关闭时，不允许发起普通实施签到；
- 定位失败、超出项目范围、跨天未签退等情况必须有明确异常状态和补录/审批规则。

## 2. 当前工程中的实际流程

### 2.1 项目入口

入口：`pages/ops/home.vue` → 项目管理 → `pages/ops/project.vue` → `pages/ops/projectDetail.vue`

当前项目详情按项目状态显示：

- 未开始 / 筹备中：开始实施；
- 实施中：临时邀约、申请还料、申请延期、提交验收；
- 已完成 / 质保中：交付日期、质保周期、报告和验收记录。

问题：

- “开始实施”只显示成功提示，不调用接口、不更新状态；
- 实施中没有“开始今日实施 / 继续实施 / 去签到”主按钮；
- “提交验收”不检查是否存在未闭环的签到记录；
- 项目详情中的实施记录只显示日期、SG 单号和内容，缺少签到、签退、时长、人员、位置、照片、用料等关键证据；
- 项目详情与实施日志页面之间没有项目参数传递。

### 2.2 实施日志入口

入口：`pages/ops/home.vue` → 实施日志 → `pages/ops/implementLog.vue`

当前行为：

- 用户进入后重新选择项目；
- 项目信息、实施记录、参与人员、行车和用料集中在一个长页面；
- 只校验“已选择项目”和“实施内容非空”；
- 提交 `/project/implementLog/save` 后显示 SG 单号并返回上一页。

问题：

- 缺少签到步骤和进行中会话判断；
- 可选所有项目，未按当前用户、当前工序和可实施状态过滤；
- 实施位置是手填文本，未与签到定位关联；
- 现场照片、人员、外协工时、用料和车辆都不是必填或条件必填；
- 提交后直接返回，没有引导签退；
- SG 单号存在 `SG + Date.now()` 前端兜底，编号责任不应落在客户端；
- 加载接口失败被静默忽略，可能把“加载失败”误表现为“无项目/无物料”。

### 2.3 已删除的独立内协打卡入口

原入口：`pages/ops/home.vue` → 内协打卡 → `pages/ops/punch.vue`。该独立页面、入口、路由和 Mock 已按产品决策删除；以下内容作为删除原因和后续项目实施闭环的反例保留。

当前行为：

- 关联单号默认硬编码为 `GZ202608141020`；
- 用户定位后可签到；
- 签到后填写工作内容，再执行结束打卡；
- 打卡记录只展示单号、日期、签到/结束时间、位置和工作内容。

问题：

- 页面定位是“内协打卡”，却被规划为运维底部主 Tab，概念范围不一致；
- 默认关联的是 GZ 故障单，不是 XM 项目或实施会话；
- `checkedIn` 仅是页面内存状态，退出页面、刷新或换设备后无法可靠恢复；
- 签退前只校验一段“工作内容”，没有校验正式实施日志是否已提交；
- 签到和签退共用一个宽泛的保存接口，缺少幂等、并发、重复点击和状态冲突处理；
- 定位失败时仍写入模拟定位，正式环境不能这样降级；
- 签退后未显示本次实施时长、SG 单号和完整闭环结果。

## 3. 建议的页面与导航改造

### 3.1 主入口统一

“实施日志”和“内协打卡”不应继续作为两个平级、互不相干的入口。独立“内协打卡”已取消，建议调整为：

```text
工作台
  ├─ 今日实施（主入口，显示当前会话状态）
  ├─ 项目管理
  └─ 实施记录（历史记录）
```

其中：

- **今日实施**：承载签到 → 日志 → 签退；
- **项目管理**：从项目详情发起或继续本项目的今日实施；
- **实施记录**：查看已完成闭环的历史会话。

被邀请的参与人员从项目详情或待办进入同一个项目实施会话，不再建设独立“内协打卡”模块。

### 3.2 建议保留一个连续页面

按照当前小程序使用场景，建议不要拆成三个互相跳转、容易丢状态的独立页面，而是在一个“项目实施”页面中展示三段状态：

| 会话状态 | 页面主内容 | 主操作 |
| --- | --- | --- |
| 未签到 | 项目/工序、人员、定位、签到说明 | 签到并开始实施 |
| 已签到，日志未提交 | 顶部固定显示签到时间与持续时长；下方填写日志 | 保存草稿 / 提交实施日志 |
| 日志已提交，未签退 | 日志摘要、用料/车辆/人员、当前定位 | 签退并完成本次实施 |
| 已完成 | 签到、日志、签退、总时长、SG 单号完整摘要 | 查看记录 / 再次发起实施 |

如用户中途离开，再次进入必须自动恢复到同一状态。

### 3.3 项目详情的操作优先级

实施中的项目详情底部操作建议改为：

1. 有进行中会话：主按钮“继续本次实施”；
2. 无进行中会话：主按钮“签到并开始实施”；
3. 次要操作收进“更多”：临时邀约、申请用料/还料、申请延期；
4. 只有所有实施会话均已闭环、用还料已结清并满足验收条件，才显示“提交验收”。

## 4. 实施闭环状态机

### 4.1 会话状态

| 状态值 | 中文含义 | 允许操作 |
| --- | --- | --- |
| `NOT_STARTED` | 未开始 | 签到 |
| `CHECKED_IN` | 已签到、待写日志 | 保存草稿、提交日志、异常取消 |
| `LOG_DRAFT` | 日志草稿 | 继续编辑、提交日志、异常取消 |
| `LOG_SUBMITTED` | 日志已提交、待签退 | 签退 |
| `COMPLETED` | 已完成 | 查看，不可普通编辑 |
| `ABNORMAL_CLOSED` | 异常结束 | 查看、发起补录/申诉 |

### 4.2 状态流转约束

```text
NOT_STARTED --签到成功--> CHECKED_IN
CHECKED_IN --保存草稿--> LOG_DRAFT
CHECKED_IN/LOG_DRAFT --提交日志--> LOG_SUBMITTED
LOG_SUBMITTED --签退成功--> COMPLETED
CHECKED_IN/LOG_DRAFT --异常结束并填写原因--> ABNORMAL_CLOSED
```

禁止：

- `NOT_STARTED → LOG_SUBMITTED`；
- `CHECKED_IN → COMPLETED`；
- `COMPLETED → CHECKED_IN`（应创建新的会话）；
- 客户端仅修改本地状态就视为流转成功。

### 4.3 最小数据模型

```ts
interface ImplementationSession {
  id: string
  projectId: string
  projectPeriodId: string
  processId: string
  implementerId: string
  status: 'NOT_STARTED' | 'CHECKED_IN' | 'LOG_DRAFT' | 'LOG_SUBMITTED' | 'COMPLETED' | 'ABNORMAL_CLOSED'
  checkInTime?: string
  checkInLongitude?: number
  checkInLatitude?: number
  checkInAddress?: string
  checkInLocationStatus?: 'NORMAL' | 'OUT_OF_RANGE' | 'FAILED'
  implementLogId?: string
  sgNo?: string
  checkOutTime?: string
  checkOutLongitude?: number
  checkOutLatitude?: number
  checkOutAddress?: string
  checkOutLocationStatus?: 'NORMAL' | 'OUT_OF_RANGE' | 'FAILED'
  abnormalReason?: string
  durationMinutes?: number
  version: number
}
```

## 5. 接口建议

接口名称最终以现有 OA 后端为准，但必须覆盖以下业务能力：

| 能力 | 建议接口 | 核心要求 |
| --- | --- | --- |
| 查询当前会话 | `GET /project/implementationSession/current` | 按用户返回唯一进行中会话 |
| 发起签到 | `POST /project/implementationSession/checkIn` | 后端校验项目/工序/人员/重复签到并返回 sessionId |
| 保存日志草稿 | `POST /project/implementationSession/log/draft` | 必须携带 sessionId |
| 提交实施日志 | `POST /project/implementationSession/log/submit` | 后端生成 SG 单号并将状态转为待签退 |
| 签退 | `POST /project/implementationSession/checkOut` | 必须已提交日志；计算时长；处理定位异常 |
| 异常结束 | `POST /project/implementationSession/abnormalClose` | 必填原因，保留审计记录 |
| 查询闭环详情 | `GET /project/implementationSession/detail` | 一次返回签到、日志、签退和关联明细 |

必须具备：

- 后端状态校验，不能只靠前端按钮禁用；
- 幂等键，防止重复点击产生两次签到或两条日志；
- 乐观锁或版本号，处理多设备同时操作；
- 服务端生成 SG 等业务编号；
- 时间以服务端时间为准；
- 经纬度、地址、定位精度、异常原因分字段保存；
- 草稿、提交、更正和异常处理均保留操作人及时间。

## 6. 其他页面与跨流程问题

### 6.1 P0：阻断业务闭环或造成错误数据

1. **角色与底部 Tab 不一致**：`pages.json` 当前固定为客户“首页 / 记录 / 我的”，运维规划中的“首页 / 打卡 / 我的”并没有真正按角色切换。
2. **状态操作是假操作**：项目“开始实施 / 提交验收”、临时邀约、报告预览等只弹提示，容易让演示状态被误认为真实完成。
3. **异常被静默吞掉**：多个列表/详情页在 `catch` 中直接忽略错误，用户无法区分“暂无数据”和“加载失败”。
4. **客户端生成业务编号**：报修、预约、维修、实施、领料、还料均存在 `前缀 + Date.now()` 兜底，可能与后端编号冲突。
5. **模拟定位进入业务结果**：签到、线下维修在定位失败时仍写入模拟地址，正式环境会产生错误考勤和现场证据。
6. **审批/验收前置条件不完整**：项目验收、维修提交审批、还料入库等关键操作需要后端再次核验，不能只由页面当前展示状态决定。

### 6.2 P1：高频操作体验和信息架构问题

1. **工作台入口过多且概念重叠**：原实现同时展示实施日志、内协打卡、项目管理；现已删除独立内协打卡入口，后续仍需把实施日志收进“今日实施”闭环。
2. **长表单缺少阶段反馈**：实施日志、预约、维修确认等页面字段较多，缺少草稿、完成度、必填标识和离开保护。
3. **详情页主次操作不清**：多个底部按钮并列，危险操作、辅助操作和主流程操作没有稳定层级。
4. **列表缺少检索与筛选策略**：项目、维修、审批、物料等列表需要状态筛选、关键词和时间范围，否则数据增长后不可用。
5. **空态、错误态、重试态不完整**：多数页面只有简单“暂无数据”，缺少原因和下一步动作。
6. **术语不统一**：“结束打卡 / 签退 / 打卡完成”“实施日志 / 实施记录”“项目单号 / 关联单号”需要统一。
7. **接单后可能丢失工单上下文**：`accept.vue` 接单成功进入线下/线上维修时需确认始终携带新接单对象的 `id`，否则目标页面会读取错误或空工单。

### 6.3 P2：上线前需要补齐的质量问题

1. 表单缺少统一的字段长度、数值范围、照片数量/大小、日期先后等校验；
2. 保存和提交缺少明确区别，弱网或失败后可能丢失大量输入；
3. 上传、定位和签名等长耗时操作缺少进度、取消和重试；
4. 状态颜色、按钮文案和提示语需要统一字典，避免页面各自硬编码；
5. 部分页面仍含“功能开发中”“角色演示入口”等开发痕迹；
6. 全局导航栏配置中标题仍是 `uniapp`，文字颜色和背景配置也需按实际端验证。
7. 巡检详情的“提交巡检”和“办结”需要共享完成度门禁，避免检查项未全部完成就越级办结。

## 7. 按角色梳理的现有业务流程

### 7.1 客户

```text
首页 → 故障报修 → 报修记录/详情
  → 信息部门派单、运维处理
  → 待确认 → 核对维修结果 → 签字 → 评价 → 完成
```

主要风险：撤回/修改/删除的状态边界、签字数据保存、评价防重复提交、维修报价确认和服务号通知仍需按真实接口验证。

### 7.2 信息部门

```text
报修列表 → 查看详情 → 派单或驳回 → 查看处理时间线
```

主要风险：派单人与接单人的职责边界、重复派单、驳回后的客户可见信息、转单后原处理人权限需明确。

### 7.3 运维维修

```text
接单 → 选择线上/线下
  ├─ 线下：预约 → 到岗签到 → 维修日志 → 结束打卡 → 还料 → 提交审批
  └─ 线上：填写维修日志 → 还料（如有）→ 提交审批
→ 管理员审批 → 客户确认/签字/评价
```

线下维修页面已经具备三段式外形，但签到、日志、结束打卡仍需要后端会话和状态约束，不能只依赖前端 `mainStep`。

### 7.4 项目实施

```text
项目列表 → 项目详情 → 签到 → 实施日志 → 签退
→ 多次闭环形成项目实施记录
→ 用还料结清 → 提交验收 → 交付/质保
```

这是本次最需要修正的流程。

### 7.5 库管与管理员

```text
库管：用料/还料申请 → 明细核对 → 出库/入库
管理员：待审批工单 → 费用与过程证据核对 → 通过或驳回
```

主要风险：数量并发、重复执行、审批意见与驳回原因、已执行记录不可篡改、前序闭环证据是否完整。

### 7.6 巡检与车辆

- 巡检：任务列表 → 分对象填写 → 自动保存 → 全部完成 → 提交/办结 → 导出；
- 车辆：行车、加油、保养三类记录，驾驶员、时间和定位自动带出。

主要风险：巡检自动保存失败的可见性、未完成红点与提交条件、车辆开始/结束里程关系、照片证据和定位失败处理。

## 8. 建议实施顺序

### 第一阶段：先补闭环（P0）

1. 新增统一的实施会话模型与接口；
2. 将项目详情主操作改成“签到并开始 / 继续本次实施”；
3. 将签到、日志、签退合并为一个可恢复状态的连续页面；
4. 日志绑定 sessionId，签退校验日志已提交；
5. 项目详情展示完整闭环记录；
6. 清除客户端业务编号兜底和正式环境模拟定位；
7. 为所有关键请求补充加载、失败、重试和防重复提交。

### 第二阶段：统一导航和术语（P1）

1. 根据角色确定真实首页和底部 Tab；
2. 删除独立“内协打卡”入口后，把项目签到/签退统一收进“今日实施”；
3. 增加“今日实施”和“实施记录”；
4. 统一状态、按钮、异常原因和业务编号文案；
5. 为列表补状态筛选、搜索、空态和错误态。

### 第三阶段：补齐异常与审计（P1/P2）

1. 跨天未签退、定位失败、超范围、无网络、重复操作；
2. 草稿恢复、日志更正、异常结束、补卡/补录审批；
3. 多设备并发和服务端幂等；
4. 上传压缩、失败重试、照片和视频限制；
5. 操作日志、版本记录和权限校验。

## 9. 验收用例

至少覆盖以下场景：

1. 未签到直接进入实施日志：禁止提交，并引导先签到；
2. 签到成功后退出小程序，再进入：恢复当前会话和已填写草稿；
3. 已签到但日志未提交，点击签退：禁止普通签退；
4. 日志提交成功：页面进入待签退状态，并显示日志摘要与 SG 单号；
5. 签退成功：显示签到时间、签退时间、总时长、两次定位和异常状态；
6. 重复点击签到/提交/签退：后端幂等，不产生重复数据；
7. 同一用户在另一项目再次签到：提示先完成或异常结束当前会话；
8. 定位失败或超范围：要求重试或填写异常原因，不得写入模拟定位；
9. 弱网提交失败：保留草稿，明确提示失败并允许重试；
10. 项目有未闭环会话时提交验收：后端拒绝并返回具体原因；
11. 已完成会话尝试普通编辑：禁止；更正必须留下审计记录；
12. 内协人员进入任务：自动带出项目、工序和会话，不允许手填任意关联单号。

## 11. 最终建议

独立“内协打卡”已经取消，但也不要只在现有“实施日志”页面顶部简单加一个签到按钮。正确做法是以 `implementationSessionId` 为中心，把签到、日志、签退定义为同一次实施会话的三个连续状态，并由后端强制校验状态流转。这样才能形成可追溯、可审计、可恢复、不能绕过的项目实施闭环。
