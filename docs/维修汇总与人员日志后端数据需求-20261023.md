# 维修汇总与人员日志后端数据需求

> 可直接转发后端的完整接口、字段、推荐统计口径及验收清单见：[发后端-维修汇总与人员日志接口需求-20261023.md](./发后端-维修汇总与人员日志接口需求-20261023.md)。其中新增路径与推荐口径需后端确认，不代表接口已经实现。

## 页面层级

维修详情仅保留“维修汇总”卡片；查看详情 → 人员维修记录 → 单条维修日志详情。人员记录可筛选人员、每页 5 条；从单条返回保留人员与页码。处理日志独立显示工单动态。

当前未取得墨刀对应稿件，沿用现有项目样式，不声称已按设计稿逐项还原。

## 现在已有的数据

- 维修状态：维修详情 `order.workStatus` 的现有映射。
- 维修人：维修详情 `order.responsibleUserName`。
- 累计维修工时：沿用 `order.effectiveDurationSeconds`，转换为 h。空值显示“待接口提供”，0 显示 0.00h。请确认此字段是整单各人员有效工时总和，而不是自然历时；明确进行中的作业、补卡、退出人员和并行作业口径。
- 当前可见日志：详情的 `workRecords`，按 `operatorUserId` 筛选，`operatorNameSnapshot` 显示姓名。当前为前端分页，不能把其长度当作整单维修次数。
- 单条详情仍调用现有 `/repair/work/detail?orderId=...&recordId=...`，沿用后端操作权限。

## 请后端提供的整单汇总（建议字段，尚未作为已存在字段对接）

建议放在现有 `/repair/order/detail` 的 `workSummary` 中；也可独立接口，路径及结构需最终确认。

| 建议字段 | 页面文案 | 统计要求 |
| --- | --- | --- |
| participantCount | 参与人数 | 实际维修参与人员去重；明确日志操作人与用人记录是否都计入，外协人数另行说明，不拿当前协助成员数代替 |
| workRecordCount | 维修次数 | 有效作业记录数量；明确草稿、缺卡及作废记录如何统计 |
| latestWorkAt | 最近维修时间 | 明确取最近签到/有效开始时间，不能混用日志修改时间 |
| effectiveDurationSeconds | 累计维修工时 | 可继续使用现有 order 字段，或统一到汇总，但不要重复、冲突 |

上述缺失项目前页面显示“待接口提供”，卡片中可展开“后端待补数据”查看说明。没有用当前授权可见记录伪造整单汇总。

## 人员日志分页（待后端确定接口路径）

请求：`orderId` 必填，`operatorUserId` 可选，`pageNo/pageSize`。建议返回 `{records,total,personOptions}`；人员候选包含历史参与人，并遵守当前用户读取权限。筛选不能扩大访问范围。

每条至少：`recordId/operatorUserId/operatorName/workRole/repairMethod/recordStatus/formStatus/effectiveStartedAt/effectiveEndedAt/durationSeconds/repairDescription`。可沿用现有 workRecords 字段名，只需最终对齐；操作权限继续从单条详情获取，不由列表推导。

汇总与列表应明确整单统计和权限可见范围的差异；无权查看某人日志时，不暴露人员信息。后端分页可用后再替换当前前端分页，不新增猜测路径的请求。
