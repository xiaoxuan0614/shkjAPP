# 维修业务流程与页面对接规则

更新日期：2026-10-22。依据：用户最新确认及《维修模块前端接口调用指南-20261022》。本轮实际实现、未完成项和验证证据见 [接口迁移记录](./维修模块接口迁移记录-20261022.md)。下方标为历史快照的内容不再作为当前接口要求。

报价操作唯一前端权限依据为整单详情 `result.canChangeQuotationDecision === true`；不再根据状态文案或通用 `canOwnerApply` 推算。最终维修价与已审批并经客户确认的价格不同，前端必须填写变更原因；无需报价不发送金额及变更原因。需要报价但尚无客户确认金额时阻止提交，不擅自用报价合计代替确认价。

## 报修人修改与取消（2026-10-22 已接接口）

- 报修单处于待处理状态时，报修人本人可以修改报修内容或取消报修。
- 开始处理后，不再允许报修人修改或取消。后端须在提交时再次核验当前状态和本人身份，避免页面打开后已开始处理仍能操作。
- 修改调用 POST `/repair/order/reportEdit`：orderId、原报修八字段及必填 reason（最多1000字符）；全量保留需要的 fileIds，可主动移除附件。
- 取消调用 POST `/repair/order/reportCancel`：仅 orderId、必填 reason（最多1000字符），不复用维修申请关闭。后端直接 CLOSED / REPORTER_CANCELLED，保留记录、关闭待办、不生成评价。
- 两个入口分别读取详情 actions.canEditReport / canCancelReport，不给列表逐条查询权限。接口条件比“待处理”更严格：须原 reporterUserId 且从未发生后续业务；初次自动派单和本人报修修改不阻断，作业、报价、申请等含撤回/软删历史均阻断。前端不通过负责人或管理员身份推导权限。
- 修改不重新派单；同分期保留联系资料，换分期由后端读取新分期资料。本轮源码及替身回归已通过，真实接口部署/业务提交验收仍需确认。

## 最新接口对齐：报价决定与完工提交

2026-10-21 再次读取 Apifox 后，前端已将报价办理改为 POST /repair/quotation/decision：无需报价只传 orderId、quotationRequired=false、reason，不显示或提交故障及维修范围；需要报价同时提交 faultScope 和 items 并发起审批，不再调用 quotation/submit。当前接口不支持“先保存需要、稍后补明细”，覆盖下文旧分步方案。两种分支均不回传 version/requestId。

完工使用 POST /repair/completion/submit，必须先有整单 quotationRequired 布尔决定；false 只传 orderId、description，true 增加 finalAmount。后端已将 amountChangeReason 改为选填，前端按用户此前明确要求仍在金额变化时必填并传入；无需报价不发送金额或旧原因。以上仅完成源码及替身回归验证，尚未真实业务提交验收。

## 最新覆盖规则：签退后操作仅为前端分支

用户最新确认取消向后端传维修结果。下文第五节旧三状态方案及“签退前必须选择报价决定”不再作为签退规则。

- 负责人签退页选择“提交完成 / 需要复修”，仅决定下一页面，不传 repairStatus、repairResult 或 reworkReason，不作为已保存结果展示。
- 提交完成：签退与详情刷新成功后，当前负责人仍有申请权限才进入提交完工页面；不自动发起审批。失败留在签退页，刷新失败提示核对，不重复签退。
- 需要复修：正常签退并返回详情；内协签退同样返回详情，不进入负责人完工页。
- 完工页需要报价才要求最终维修价格，默认客户确认价；金额不同必填原因。不需要报价时隐藏价格，不发送金额和陈旧变更原因。
- 完工审批仍由用户确认提交，报价、还料、权限等由后端最终校验；未判断报价不擅自按无需报价处理。
- 页面分支和价格显隐/校验已实现；2026-10-22 已迁移新日志接口，但不能据此宣称全链路已联调。

本文为当前目标规则，优先于旧文档中“日志内选择是否报价”“日志内填写维修结果”“签到选车辆和参与人”等描述。目标规则不代表后端已部署，当前实现边界见文末。

## 一、单据与人员范围

- 所有人可以报修，填写客户、项目、项目下产品、故障现象、报修时间、备注和附件。
- 根据排班自动分配负责人，正常报修不增加人工指派步骤。
- 报修列表：主管查看全部，运维人员查看分给自己的报修单，其他人员查看本人报修；权限最终由后端控制。
- 维修列表默认“我负责的全部”，范围 RESPONSIBLE；协助任务使用 HELPING，不由列表范围推导操作权限。
- orderId 标识整张维修单；recordId 标识每次签到生成的维修记录。一张维修单可以有多次维修记录。

## 二、主流程

报修 → 排班分配 → 负责人查看 → 签到 → 填写/保存草稿 → 提交本次日志 → 选择结果并签退 → 必要时再次维修 → 提交整单完工审批 → 主管审批 → 客户评价。

报价、协助、领还料、转单、关闭是关联业务，不与本次日志的草稿、提交、签退状态混为一谈。首次签到和检查不以已填写报价单为前提。

## 三、报价独立于日志

### 页面与保存

- 在维修单详情单独展示“报价管理”，不在维修日志表单中展示报价状态、是否报价选择或报价入口。
- 每单由负责人明确选择“需要 / 不需要”，初始为“未选择”，不能默认为不需要。
- 当前接口选择需要时必须同时填写范围和明细，并提交报价审批；不支持单独保存“需要”空决定。
- 未选择不阻止签到、检查、草稿或签退，提交整单完工前必须明确并完成相应报价分支。
- 日志提交、修改、草稿恢复不能覆盖整单报价决定。

### 修改与锁定

- 客户确认前允许调整是否需要报价。
- 改为不需要时填写变更原因，终止现有待审批、审批中、审批通过待客户确认的报价流程。
- 终止后旧报价不可继续审批、客户确认；历史报价、审批及变更记录保留。
- 后端将修改决定与终止流程作为同一事务，处理与审批、客户确认的并发冲突。
- 客户确认后锁定是否需要报价。前端只读，后端仍须校验，不能仅靠按钮隐藏。
- 报价流程：填写报价单 → 运维主管审批 → 总经理审批 → 内部登记客户确认及价格。审批驳回可修改重提；客户无需登录系统。

## 四、签到与日志填写

- 签到选择维修方式（线上、线下、检修），实际定位；不选择车辆、作业阶段或参与人员。
- 签到返回的 recordId 必须贯穿本次草稿、提交、修改和签退，不能重新生成或拿 orderId 替代。
- 恢复本人当前记录可仅用 orderId 查询；查看指定历史记录须传 orderId + recordId，防止串记录。
- 样式沿用项目实施，负责人表单分三页：
  1. 报修信息：只读客户、项目、产品、报修人、报修时间、故障现象、附件。
  2. 维修信息：故障描述、维修内容、维修照片/视频；不填故障位置、不填报价决定、不选维修结果。
  3. 用人、用车、用料：本次实际投入及实际用料记录。
- 切页保留输入；提交校验失败回到对应页面。第三页提供保存草稿、提交日志进入签退。
- 负责人正式提交至少一张照片或一段视频，最多六张照片、两段视频；草稿允许不完整。
- 用料关联已有真实用料记录，关联操作不重复扣库存或篡改数量、确认状态。

### 日志接口分工

| 接口 | 用途 |
| --- | --- |
| POST /repair/work/saveDraft | 保存未完成内容，仍校验登录、归属、可编辑状态 |
| POST /repair/work/submit | 首次正式提交，不签退、不默认完成、不自动报价 |

## 五、签退后去向

- 负责人选择“提交完成 / 需要复修”，只决定签退后的页面；不向后端传维修状态或复修原因。
- 按本次 `actions.canEnd` 放行，必须先正式提交；签退只传 `orderId/recordId/location`。
- 提交完成：签退和整单详情刷新成功，再根据负责人申请权限进入完工表单，不自动提交审批。
- 需要复修或内协：签退后返回详情。报价状态不阻止签退。
- 签退接口明确幂等，传输失败可只重试签退；前端不自行累计工时或结束整单。

## 六、内协与关联申请

- 内协选择对应维修单，签到、填写维修内容、签退；不填写负责人信息、报价、故障、资源或负责人维修结果，不强制附件。
- 内协按本次记录 `workRole=COLLABORATOR` 简化填写，签退使用同一定位接口；修改时仍携带原有可选关联，避免全量替换清空历史数据。
- 协助由负责人申请，选择公司用户（可多选）及原因；运维主管和所选人员角色对应主管都通过后才加入。
- 领料、还料沿用项目申请模式；领料选择全量物料，经主管审批后库管出库。实际用料与申请分别记录。
- 转单填写个人问题/病假等原因及备注，由主管审批并确定新负责人。
- 关闭填写客户弃修/不是问题/其他及备注，主管审批通过后才关闭。

## 七、完工与详情

- 所有维修完成后，由负责人申请整单完工；已确认报价时再次核对维修价格，可修改并展示累计维修时长。
- 完工前后端核验还料是否完成；后端依据申请、使用、归还记录计算，不信任前端自行结清。
- 运维主管审批，通过后进入客户评价；驳回填写原因，可继续维修、打卡并重新提交。
- 详情按 recordId 展示每次日志、人员、车辆、用料、照片、签到签退及结果，不能混用整单资源。
- 内协历史可见性、角色操作权限由后端返回；前端不扩大权限。
