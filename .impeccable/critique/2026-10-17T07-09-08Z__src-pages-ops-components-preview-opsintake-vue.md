# 运维页面逻辑调整方案

日期：2026-10-17。方法：双独立评审（A：ops_business_review；B：ops_ui_evidence）。本次只读评审，未修改页面业务代码。

业务依据：[运维报修维修流程-后端对接说明](./运维报修维修流程-后端对接说明.md)。其中建议和未确认边界仍需对齐，不擅自变成确定需求。

## 结论

现有页面表达旧的“受理→勘查→内部确认报价→生成维修单”；新需求是“报修→自动分配→首次维修打卡检查→判断报价→继续维修→完工审批”。必须先改状态、权限和页面职责，不能只追加按钮。保留现有项目风格，不重新设计色调。

## 页面职责与建议结构

### 1. 首页日常办公

保持原有样式，按业务身份展示相关入口。报修入口所有人可见；报修列表范围由后端决定；维修列表面向负责/协助任务人员和主管；报价作为维修关联业务的聚合入口，不再作为生成维修单的前置步骤。审批从首页待办进入具体申请，不把主管查看权限直接当负责人执行权限。

巡检本轮不改。

### 2. 创建报修

关联信息：客户→项目→项目产品；故障、年月日报修时间、备注、附件。报修人自动记录。切换上级时清除失效下级；项目产品单/多选和无产品报修规则仍待确认。继续复用 SectionCard 和公共附件组件。

### 3. 报修列表与详情

列表显示报修人、客户、项目、报修时间、主状态；待处理显示等待时间。筛选为全部/待处理/进行中/已完成，建议另加已关闭。保留搜索、分页与新增悬浮按钮。

详情主要展示报修信息、附件和处理进度，不再嵌入“受理→勘查→内部确认”的整套执行表单。具备权限者通过关联入口进入维修详情。

### 4. 维修列表与详情

列表建议区分我负责的、我协助的、历史负责；主管可查全部。历史负责只读，协助权限待双审批通过后生效。

详情结构：

```text
状态区：主状态 + 当前细状态 + 等待谁/阻断原因
报修信息摘要：客户、项目、产品、报修人、故障
维修日志：最近一次优先，历史可展开
报价：当前阶段、审批进度、客户确认价
参与人员：负责人、已加入、协助审批中
物料：领用、使用、还料、未结清明细
审批与流转：报价、协助、转单、关闭、完工历史
底部：当前主操作 + 协助/物料 + 更多（转单、关闭）
```

当前主操作根据允许操作集合选择：开始维修、继续填写、提交/修改报价、客户确认维修、继续维修、提交完工。等待审批时明确说明等待对象；不能只显示笼统“待确认”。不是将所有按钮同时铺开。

### 5. 统一维修日志

统一为开始打卡→检查与报价判断→维修记录/用车用人/照片→维修结果→结束打卡。线上、线下、检修在日志内选择，不再三套独立业务流程。不同类型的定位要求另行确认。

报修与项目维保类型只读展示，不通过填写日志覆盖源数据。首次检查需要报价时可结束本次日志；报价未确认禁止开始后续维修。日志结果只有维修完成/需要复修，复修填原因，客户弃修进入关闭申请。

### 6. 独立申请与审批

- 报价：明细→主管审批→总经理审批→客户确认维修并记录价格。驳回可修改重提。
- 协助：负责人选择人员和角色，展示两位主管审批进度；未全通过人员与已加入人员分开。
- 转单：负责人选原因、填备注；主管审批时指定新负责人。
- 关闭：原因和备注，显示未结束打卡、未结清物料；主管通过才关闭。
- 完工：累计时长、物料结清、客户原确认价及最终价；修改最终价格无需再次客户确认；主管驳回可继续维修。
- 客户评价：完工通过后生成，不能展示固定五星作为真实结果。

## 状态及演示数据改造

1. 报修和维修使用同一组关联 ID，不再各自维护互不回写的旧阶段。
2. 主状态、报价状态、各类申请审批独立建模，定义允许组合。
3. 权限区分查看、负责人执行、协助执行、主管审批；正式接口返回 allowedActions，前端不能替代后端鉴权。
4. Mock 场景覆盖：待处理、首检报价、一级/二级审批、客户确认、复修、协助半通过/全通过、转单历史、未结清阻断、完工驳回、已完成及已关闭。
5. 仍无正式接口时继续清楚标注演示，不让本地切换状态冒充真实审批或上传成功。

## 实施顺序

1. 状态、身份权限、报修/维修关联数据模型。
2. 创建报修、两类列表和维修详情职责调整。
3. 统一维修日志和报价门禁。
4. 协助、转单、关闭、完工提交及审批详情。
5. 收口首页预览与旧 repairRecord/repairDetail 路由，防止两套流程并存。
6. 角色、状态转换、重复提交及移动端交互回归，再做样式收尾。

旧路由当前仍有 /ops/repairRecords 请求，未取得新后端文档前不得直接把它当作新流程接口。

认知负担：普通报修人面对五个运维入口；报修七个筛选、维修八个筛选混合多种状态；等待状态不指明办理人。应减少跨页面记忆，以主状态和当前下一步组织信息。

风险：手机报修人可能误解数据范围；负责人可能将内部确认当作客户确认、将关闭申请当直接关闭；主管缺专属审批上下文。审批等待阶段应明确谁在办理、当前能做什么。

优点：演示边界提示清晰；搜索/每页五条/悬浮新增已具备；公共附件和项目样式组件可以继续复用。

建议对应动作：clarify（职责与状态命名）、harden（权限和审批约束）、distill（详情信息分组）、polish（最终视觉与移动端收尾）。
